# 国际化（i18n）二次优化改造计划

## 目标与验收标准

- 目标：在中文（简体，`zh-CN`）语言环境下，遍历项目内所有页面及其可达子页面，消除 UI 中残留英文（含按钮/提示/表单/错误/空状态等），并覆盖易遗漏位置（页面标题、浏览器标签、`aria-label`、图片 `alt`、`title`、`placeholder`）。
- 验收标准：
  - 在 `zh-CN` 下完成全页面巡检截图；截图中不出现未本地化英文（允许的例外需显式列入白名单并说明原因，例如产品名/专有名词/代码片段/URL）。
  - i18n 自动化扫描报告（E2E）中：`missing-key` 为 0；`hardcoded` 与 `incomplete-translation` 为 0（或仅剩白名单项）。
  - 动态文本（插值/日期/复数等）在 `zh-CN` 下显示自然、无乱码、格式符合预期。

## 现状复用点（基于仓库已有实现）

- i18n 体系为自研 `I18nContext` + `useTranslation(namespace)`：按 `i18n/locales/{lang}/**/*.json` 预加载，namespace 由文件路径推导（去掉 `i18n/locales/{lang}/` 前缀与 `.json` 后缀）。
- Playwright 已存在 i18n E2E 主套件 `tests/e2e/i18n/i18n-e2e.spec.ts`：
  - 启动 Electron 时会在临时配置目录写入 `preferences.json`，默认 `language: 'zh-CN'`，满足“切换到中文并正确加载配置”的前置条件。
  - 已实现可见文本与关键属性（`title/aria-label/placeholder/alt`）采集与问题分类（缺 key / 硬编码 / 不完整翻译）。
  - 已有基础“路由巡检（Crawler）”框架，但目前未做逐页截图，且未覆盖详情子页（如会话详情、Source/Skill 详情、弹窗/抽屉等）。

## 工作流总览

1. **基线巡检（Before）**：在 `zh-CN` 下自动遍历页面 + 截图 + 生成问题报告（JSON/Markdown）。
2. **问题定位与修复**：逐条定位英文来源（硬编码/漏 key/引用错误/缺少 zh-CN 条目），补齐翻译或改为 `t()` 引用，并补充无障碍与标题类文本。
3. **回归巡检（After）**：同样遍历 + 截图 + 生成报告；对比 Before/After 截图与问题清单，确保清零或按白名单收敛。
4. **迭代回归（不限次数）**：若 After 截图中仍出现需要改造的英文，则继续“修复 → 回归巡检”循环，直至截图中不再出现需要改造的英文。
5. **交付整理**：输出截图与修复记录、翻译条目清单、对比截图索引。

## 详细执行步骤

### 1) 语言环境锁定为中文（简体）

- 复用 E2E 启动逻辑：在测试专用配置目录写入 `preferences.json`，强制 `language: 'zh-CN'`。
- 额外校验点：
  - 在应用启动后读取/断言当前语言状态（通过 UI 或注入 `window` 侧状态），确保没有被默认值或历史数据覆盖。

### 2) 系统性遍历“所有页面及子页面”

#### 2.1 Electron 主应用（渲染进程）

- **主导航页面（route 级）**：
  - Sessions：`allSessions`、`flagged`、`archived`、`state/{id}`、`label/{id}`、`view/{id}`（后 3 类需在可行时从 UI/数据中发现可用 id，否则至少覆盖默认/空态）。
  - Sources：`sources`、`sources/api`、`sources/mcp`、`sources/local`。
  - Skills：`skills`。
  - Settings：`settings/{subpage}`，覆盖注册表中全部子页（`app/ai/appearance/input/workspace/permissions/labels/shortcuts/preferences`）。
- **详情子页（UI 交互级）**：
  - 会话详情：在 Sessions 列表中创建/打开 1 个会话并进入详情页，再覆盖典型子区域（如右侧栏/更多菜单/权限模式等可达弹层）。
  - Source 详情：从 Sources 列表点入首个可见 Source；覆盖配置页/授权入口（如存在）/删除确认弹窗（只打开不执行破坏性操作）。
  - Skill 详情：从 Skills 列表点入首个可见 Skill；覆盖详情页内的设置项/提示/空态。
  - 典型弹层/抽屉/对话框：通过点击“添加/配置/更多”等入口打开（例如 SidebarMenu、Settings 中的管理弹窗），纳入扫描与截图。

#### 2.2 Viewer Web 应用（如需要纳入“所有页面”范围）

- 路由为手写：`/`（上传页）、`/s/{id}`（会话查看）。
- 执行策略：
  - `/` 页面截图 + 扫描。
  - `/s/{id}` 通过生成/复用一条测试会话数据获得可访问 id 后截图 + 扫描。
  - 若 Viewer 目前未接入 i18n 或不在本次范围，将在最终交付中明确说明并给出纳入建议。

### 3) 截图产出与命名规范

- 截图操作方式（自动化，Playwright 驱动）：
  - 复用现有 E2E 的导航能力（通过 `craft-agent-navigate` 切换 route，或通过 UI 点击进入详情/弹层）。
  - 每次到达目标页面后执行稳定性等待：
    - `domcontentloaded` + 适度 `waitForTimeout`（必要时补充对关键节点 `locator(...).waitFor()`）
    - 若页面有滚动容器，优先保持默认首屏；对需要完整信息的页面使用 `fullPage` 截图。
  - 调用 Playwright 截图 API 输出 PNG（在执行阶段会落到代码中实现）：
    - 页面全屏：`page.screenshot({ path, fullPage: true })`
    - 关键区域（可选）：`locator.screenshot({ path })`（用于表格/右侧栏/弹窗等更易读的对比图）
- 在现有 i18n Crawler 循环中，为每个目标页面输出截图：
  - `test-results/i18n-screenshots/before/<pageName>__<route>.png`
  - `test-results/i18n-screenshots/after/<pageName>__<route>.png`
- 对详情子页/弹层，追加后缀区分状态：
  - `...__detail.png`、`...__modal-xxx.png`、`...__empty.png` 等（统一通过代码内命名表维护）。

### 4) “识别英文文本”的方法（OCR 为主，DOM 为次）

- OCR 识别（主手段，以“截图里看到的内容”为准；采用 LLM 多模态）：
  - 对 `test-results/i18n-screenshots/**.png` 逐张进行多模态识别，抽取“仍然显示为英文”的文本（含 DOM 文本、canvas 绘制文字、图片内嵌文字、SVG 路径化文本等）。
  - 执行方式：
    - 在执行阶段由多模态 LLM 直接读取截图并输出结构化结果（相当于 OCR + 语义过滤），不依赖本地 Tesseract。
    - 输出字段包含：截图文件名、识别到的英文文本、所在区域描述（例如“左侧导航/顶部标题栏/表单标签/弹窗按钮”）、以及置信度或“确定/疑似”标记。
  - 降噪规则：
    - 过滤：URL、文件路径、代码片段、版本号、快捷键组合、产品/品牌名白名单、以及用户内容（如聊天消息）中的英文（若该英文属于用户输入内容，则不作为 i18n 问题）。
  - 产出：
    - `test-results/i18n-ocr-report.json`：截图 → 英文片段清单（机器可处理）
    - `test-results/i18n-ocr-report.md`：截图 → 英文片段 → 位置描述（便于人工复核与修复分派）
- DOM 采集与定位（次手段，用于把 OCR 命中的英文“精准落到代码”）：
  - 在生成截图的同一轮巡检中，仍执行 DOM 可见文本与关键属性采集（仓库已有 `collectVisibleStrings`），并与 OCR 命中的英文进行交叉验证：
    - 若 OCR 片段能在 DOM 采集中命中，则可直接拿到 selector → 反查组件/namespace → 修复翻译或改 `t()`。
    - 若 DOM 无法命中（纯图片/canvas/webview），则以截图记录为准，走对应资源/渲染逻辑的专项修复路径，并在报告中标注为“非 DOM 文本来源”。

### 5) 定位与修复策略（逐条闭环）

- 分类处理：
  - `missing-key`：UI 中出现疑似 key（或未替换插值），检查对应 namespace 的 `zh-CN` 文件是否缺项，补齐中文翻译。
  - `incomplete-translation`：key 存在于 `en` 资源中，但 `zh-CN` 缺失或仍是英文；补齐 `zh-CN` 对应条目。
  - `hardcoded`：代码里存在硬编码英文；改为 `t()` 引用，并在匹配 namespace 的 `en/zh-CN` JSON 中补齐条目（保持 key 一致）。
- namespace 归属规则：
  - 优先放入触发组件/页面同名的 namespace 文件（例如 `pages/settings/PreferencesPage`、`components/app-shell/AppShell`），避免把无关文案堆到通用文件。
- 易遗漏点专项清单：
  - 页面/面板标题、窗口标题、`document.title`、系统菜单（Electron menu schema）文案。
  - `aria-label`、`alt`、`title`、`placeholder`、空状态/错误提示。
  - toast/notification、确认弹窗、快捷键描述、表格列头、右键菜单。

### 6) 动态内容与格式验证

- 插值文本：校验 `{{var}}` 形态替换是否正确；检查中文语序与标点是否自然。
- 日期/时间：确认在 `zh-CN` 下格式与本地化一致（必要时引入统一格式化工具或复用现有工具）。
- 复数/数量：若存在英文复数逻辑，评估是否需要中文特化规则（目前 i18n 实现未内建复数规则，需在文案层规避或定制）。

### 7) 回归与质量门禁

- 回归执行（循环直至收敛）：
  - 运行同一套“遍历 + 扫描 + 截图”，产出一次 After 结果。
  - 以“截图人工复核”为最终准绳：只要截图里仍能看到需要改造的英文，就继续下一轮修复与回归（不限次数）。
  - 每一轮回归都更新报告与截图索引，确保问题条目可追踪、可验证、可复现，直至截图不再出现需要改造的英文。
- 防回归建议（可选）：
  - 将“i18n 扫描 + 截图”作为 CI 的非阻塞检查或在发布前手动门禁运行。

## 交付物清单（满足你的 3 项要求）

1) **所有发现问题的截图及对应修改记录**
- `test-results/i18n-screenshots/before/`：改造前全页面截图

- `test-results/i18n-translations-changelog.md`：按 namespace 列出新增/修改的 key 与中文译文（从变更的 `zh-CN` JSON 自动汇总生成）

3) **改造后的页面截图对比**
- `test-results/i18n-screenshots/compare.md`：每个页面提供 Before/After 的图片引用与问题关闭情况摘要

## 实施假设（可随执行中调整）

- Electron 应用已可本地编译并可被 Playwright 启动（现有 E2E 已有该前置检查）。
- “所有页面及子页面”以“可通过导航或常见交互可达的 UI 状态”为准；不可达/需外部依赖（第三方登录、真实网络资源）的页面将通过 mock/跳过并在报告中标注原因。
